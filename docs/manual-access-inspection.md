# IDOR·권한 검증 수동 비교 및 기록

## 범위와 사용자 흐름

기존 `/services` 또는 저장소 분석 화면의 IDOR·권한 검증 탭에서 수동 대상을 등록합니다. 자동 정적 분석 후보를 생성하거나 HTTP 요청·계정 인증·리소스 탐색·권한 우회를 수행하지 않습니다. SQLi/XSS 자동 관찰 registry·전송기·승인·요청 예산은 변경하지 않습니다.

1. API 상대 경로·HTTP 메서드·검사 목적·기대 동작을 입력합니다. 메서드는 수동 결과를 설명하는 값이며 POST/DELETE를 선택해도 요청하지 않습니다.
2. IDOR: 테스트 계정 A/B의 별칭, 각자 소유한 서로 다른 합성 리소스 ID, 식별자 위치를 입력합니다. A→A, A→B, B→B, B→A의 기대 접근을 각각 허용·거부·확인 불가로 지정합니다. 실계정 소유 관계는 서버 미검증입니다.
3. 권한 검증: 허용·거부 역할을 쉼표로 등록하고 기본 API 작업을 지정합니다. 역할은 중복·허용/거부 중첩 없이 2~4개, 작업은 1~4개입니다. 추가 작업마다 이름·API·메서드와 모든 역할의 기대 접근을 설정합니다. 미확정 정책은 확인 불가로 남깁니다.
4. 기대 정책 확인 후 기존 확정 대상 history에 새 버전을 생성합니다. 계정·리소스·역할·API·작업·기대 정책도 target identity에 포함됩니다.
5. 검사 결과 기록 화면의 비교 표에 승인된 격리 환경에서 직접 얻은 최초 관찰과 재검증을 입력합니다. 상태 코드, 사용자 선택 접근 결과, 비밀 없는 응답 요약, 판단 근거, 관찰 SHA·수행 일시·격리 환경 확인을 각각 기록합니다. 계정이나 역할의 비밀번호·쿠키·토큰을 넣는 필드는 없습니다.
6. 계정·리소스 또는 역할·작업별 비교와 최초/재검증 비교를 확인합니다. 응답 차이는 사용자가 입력한 요약 문자열의 차이이며 실제 HTTP 본문 바이트·서버 로그 검증이 아닙니다.
7. 필요하면 비교 요약을 기존 `SecurityTestRecord`의 최초/후속 수동 메모로 복사합니다. 검사 상태·직접 수행 확인·재검증 완료를 자동 선택하지 않습니다. 수정 파일·내용·방법과 사용자 판단을 작성한 후 DB 저장을 별도로 수행합니다.

## 기대 정책과 관찰의 분리

- HTTP 200 또는 403만으로 접근을 추정하지 않습니다. 접근 허용·거부는 사용자가 별도로 선택하고 응답 요약·판단 근거를 작성해야 합니다.
- 수행 정보·격리 환경 확인·유효한 관찰 SHA 또는 근거가 부족하면 유효 관찰은 확인 불가입니다.
- 기대 거부/관찰 허용은 **권한 정책 위반 의심 · 서버 미검증**입니다. 기대 허용/관찰 거부는 예상 밖 거부이며 인증 실패나 환경 오류 등의 원인은 별도 확인해야 합니다. 일치도 사용자 관찰일 뿐 서버 검증 성공이 아닙니다.
- 모든 행의 결론을 알 수 없어도, 확인 불가의 응답 상황과 이유를 기록할 수 있습니다. 재검증 기록 완료에는 두 단계의 수행 정보와 각 사례의 요약·근거 및 기존 수동 재검증 필수 항목이 필요합니다.
- 관찰 SHA는 사용자 진술입니다. 최초 단계는 저장된 분석 SHA에 묶고, 재검증 SHA는 별도 필드에 보관합니다. 재검증 SHA를 입력해도 기존 저장소·분석 SHA·AnalysisRun 연결이나 대상 버전을 바꾸거나 새 커밋의 분석 완료를 증명하지 않습니다.
- 구조화된 수행 일시는 UTC ISO 문자열로 저장·미래 여부를 검증하고 기기 시간대로 표시합니다. 기존 `performedAt` wall-time 필드는 구조화된 재검증 일시의 표시용으로 동기화합니다. 서버 시간대가 브라우저와 달라도 UTC 관찰 일시를 기준으로 검사합니다.
- 재검증 수행 일시는 최초 관찰보다 이전일 수 없습니다. 잘못된 순서는 화면에서 안내하고 서버 저장 검증에서도 거부합니다.

## JSON 가져오기와 인증정보 제외

가져오기는 사용자가 붙여 넣는 **전용 JSON 양식만** 지원합니다. URL 요청·파일/브라우저 인증정보 자동 수집·원본 HTTP/HAR·헤더 가져오기는 없습니다. 양식은 현재 대상에서 볼 수 있습니다.

- 저장소, 분석 SHA, recordKey, 전체 target identity, 최초/재검증 단계가 모두 일치해야 합니다.
- 정해진 사례 ID와 상태 코드·접근 결과·응답 요약·근거·수행 정보만 허용합니다. 추가 필드, 잘못된 enum·일시·길이, 다른 대상·단계·분석의 결과는 거부합니다.
- 가져오기 텍스트는 Provider나 DB에 저장하지 않으며 처리 후 지웁니다. 알려진 인증 헤더·Cookie/Set-Cookie·비밀번호·토큰/세션 키·Bearer/JWT·URL 사용자 정보 패턴은 화면 입력과 서버 저장 검증에서 거부합니다. 자격증명 수집 기능은 없으며 사용자도 합성 자료의 비밀 없는 요약만 입력해야 합니다. 임의의 의미 없는 문자열이 실제 비밀인지 자동 판별하는 기능은 아닙니다.
- 가져오기 성공은 현재 화면 반영일 뿐 DB 저장 완료나 서버 검증이 아닙니다. DB 저장은 기존 API의 성공 응답을 확인해야 합니다.

## 버전·상태 유지와 저장

기존 `useSecuritySession`, `useConfirmedPracticeTarget`, `practiceRecordKey`, `SecurityTargetRecords`를 사용합니다. 등록 초안·비교 표는 같은 분석 화면에서 탭 전환·준비/기록 이동·컴포넌트 재진입 중 유지됩니다. 새로고침·전체 페이지 이탈 후에는 DB에 저장한 기록만 복원할 수 있습니다.

정책이나 대상 변경 시 현재 확정 상태를 해제합니다. 재확정하면 새 버전과 빈 비교 기록을 만들며 이전 버전은 화면 흐름에서 읽기 전용으로 보존합니다. 이전 분석의 전체 초안 요약에도 비교 표를 읽기 전용으로 표시합니다. 이전 자료를 다른 대상의 새 관찰로 표시하지 않도록 비교 자체의 target identity도 검사합니다.

Prisma 모델·마이그레이션은 변경하지 않습니다. 기존 `SecurityTestRecord.draft` JSON에 선택 필드 `accessComparison`을 추가했습니다. 확정 정책은 `targetSnapshot.details.accessPlan`에 있으며 target identity에 포함됩니다. UI에는 내부 JSON 대신 비교 표로 표시합니다.

- 기존 기록에 선택 필드가 없으면 기존 일반 수동 UI로 표시합니다.
- 서버는 `parseRecord`에서 정책과 모든 관찰을 다시 검증하며 출처는 기존처럼 MANUAL입니다.
- 기존 로그인 사용자별 조회·수정 제한, 완료 분석의 사용자/저장소/SHA 확인, 대상 identity 변경 차단, revision 충돌 감지를 재사용합니다. 타인의 자료에 접근할 권한을 주는 기능이 아닙니다.
- DB 미적용 및 연결 실패 안내를 재사용하며 저장 실패를 성공으로 표시하지 않습니다. `/results/[id]`도 동일한 구조화된 표와 기존 저장/수정 UI를 사용합니다.
