## 발견한 문제

1. 기존 syncAllUserInstallations는 현재 보이는 설치만 순회했다. 설치 자체가 목록에서 사라지면 과거 UserRepository.active가 유지될 수 있었다.
2. 선택 저장소에서 제거된 저장소는 설치 동기화 시 비활성화됐지만, 설치 중지나 Contents 권한 변경을 연결의 읽기 가능 상태에 충분히 반영하지 않았다.
3. 기존 분석 API는 연결 ID + userId + active 및 DB 설치 중지를 검사한 뒤 설치 토큰으로 수집했다. 조직 탈퇴나 사용자 권한 회수 후 DB가 오래됐을 때 설치 토큰의 권한이 사용자 권한을 대신할 수 있었다.
4. 기존 AI API도 같은 DB 검사 뒤 분석 캐시 및 LearningRecord를 반환했다. GitHub에 재접속하지 않고 캐시를 반환할 수 있었다.
5. 기존 다른 사용자 연결 ID 차단 쿼리 자체는 userId로 제한돼 있었다. 이를 공통 검사로 유지하고 설치 행의 사용자도 검증했다.
6. 공개 URL 분석 수집기는 서버 GITHUB_TOKEN과 자체 소스 캐시를 사용할 수 있다. 따라서 App 연결 API 보완만으로는 서버 토큰이 읽을 수 있는 비공개 저장소나 공개→비공개 전환 직후의 캐시 우회를 충분히 막지 못했다.
7. 기존 10페이지 제한에서 남은 페이지가 있어도 목록을 완전한 스냅샷처럼 사용할 수 있었다. 권한 동기화에 불완전한 목록을 사용하면 잘못된 승인/해제 상태를 만들 수 있다.

## 해결 방식

### 연결 저장소의 공통 접근 검사

requireRepositoryAccess(userId, connectionId)는 다음 순서로 검사한다.

1. 현재 사용자 소유이며 active인 연결만 DB에서 찾는다. 없으면 존재 여부를 구분하지 않고 404로 종료한다. 연결된 설치 행의 사용자도 일치해야 한다.
2. 요청한 사용자의 GitHub user access token을 기존 방식으로 조회/갱신한다.
3. 캐시 없이 `/user/installations` 전체 목록에서 설치를 확인한다.
4. 최신 설치의 suspended_at이 null이고 Contents read/write 권한이 있는지 확인한다.
5. 같은 사용자 토큰으로 `/user/installations/{id}/repositories`를 확인한다. 저장된 GitHub 저장소 숫자 ID 및 명시적인 읽기 권한이 일치해야 한다. 이름만으로 승인하지 않는다.
6. 현재 full_name과 DB의 이름도 비교한다. 이동/이름 변경 시 409를 반환하고 동기화를 요구한다.
7. 설치별 목록은 Metadata 권한만 필요하므로, 사용자의 실제 Contents 읽기 가능 여부도 `/repos/{owner}/{repo}/contents` 루트 디렉터리 요청으로 확인한다. 설치 토큰으로 이 검사를 대체하지 않는다. 실패나 비정상 응답은 차단한다.

사용자 권한 확인에는 15초 요청 타임아웃을 사용하고, GitHub 요청은 기존 githubJson의 no-store 방식을 사용한다. 권한 검증 결과는 캐시하지 않는다.

GitHub 공식 근거:

- [사용자 토큰이 접근할 수 있는 설치 및 설치별 저장소](https://docs.github.com/en/rest/apps/installations): 설치별 저장소는 사용자에게 명시적으로 허용된 목록이며, 해당 목록 API의 요구 권한은 Metadata read이다.
- [저장소 Contents API](https://docs.github.com/en/rest/repos/contents#get-repository-content): 경로를 생략하면 루트 디렉터리를 반환하며 Contents read 권한을 요구한다.

### 상태 동기화와 안전한 실패

- 완전한 설치 목록에서 빠진 설치의 연결을 현재 사용자 범위 안에서 비활성화한다. 설치가 0개이면 이 사용자의 모든 연결을 비활성화한다.
- 중지되거나 Contents 권한이 없는 설치의 저장소는 재활성화하지 않는다.
- 설치별 허용 목록에서 사라지거나 명시적인 읽기 권한이 없는 저장소는 비활성화한다.
- 페이지 전체 수, 항목 수, 중복 ID, 중간 total_count 변경을 검증한다. 기존 최대 10페이지/1,000개 제한을 넘거나 부분 응답이면 오류로 중단한다. 잘린 스냅샷으로 권한을 확정하지 않는다.
- 개별 API 검사에서 최신 목록으로 설치/저장소 권한 회수가 확인되면 해당 사용자 연결을 비활성화한다.
- 네트워크 장애, 요청 제한, GitHub 403/404 응답의 모호한 원인, 토큰 오류, 불완전한 응답은 보호 데이터를 반환하지 않는다. 일시 장애를 확정된 권한 회수로 오인해 영구 비활성화하지는 않는다.
- 복구 후에는 기존 목록 동기화/App 연결 흐름으로 권한이 확인된 연결을 재활성화할 수 있다.

| 상황 | 연결 API 처리 |
| --- | --- |
| 로그인 없음 / GitHub 사용자 인증 만료 | 401 |
| 다른 사용자 연결 ID / 비활성 연결 | 404 |
| 최신 목록에서 권한 회수가 확정됨 | 403 및 해당 연결 비활성화 |
| 저장소 이름/이동 정보 불일치 | 409, 동기화 필요 |
| GitHub 장애·제한·Contents 검사 실패·검증 불가 | 503, 데이터 반환 없음 |

홈과 내 저장소, 저장소 목록 API도 저장된 정보를 반환하기 전에 권한을 동기화한다. 홈의 LearningRecord는 현재 활성화된 사용자 소유 연결이 있는 저장소로 제한한다. 페이지에서 동기화가 실패하면 기존 목록으로 대체하지 않고 서버 오류 경로로 중단한다. 새로운 UI 화면은 만들지 않았다.

### 기존 결과 및 AI 캐시

- 분석 API는 소스 수집/AST 캐시 조회 전에 공통 검사를 수행한다. 소스 수집 후에도 다시 검사하고, 권한을 잃으면 결과를 반환하거나 AST 캐시에 추가하지 않는다.
- AI API는 최신 분석 기록, 메모리 분석 캐시, DB AI 캐시를 읽기 전에 공통 검사를 수행한다.
- AI 설명 생성이 진행되는 동안 권한이 회수되면 생성 완료 후 재검사에서 차단하고 결과를 DB에 저장/반환하지 않는다. 설명 생성 함수와 프롬프트는 바꾸지 않았다.
- AI 캐시의 userId_cacheKey 제한과 분석 기록의 requestedByUserId 제한을 유지했다.
- 보호 API 응답은 Cache-Control: private, no-store로 표시한다. 연결 API는 Vary: Cookie도 설정한다.
- 공유 소스/AST 캐시와 기존 LearningRecord는 삭제하지 않는다. 현재 권한을 통과한 사용자만 조회할 수 있게 반환 경계를 보호한다. 설치별 캐시 네임스페이스도 유지한다.
- 이미 사용자 브라우저로 전달되거나 사용자가 저장한 데이터는 서버에서 회수할 수 없다. 이번 변경은 이후 요청의 반환을 차단한다.

### 공개 URL 경로의 우회 차단

- `/api/analyze?source=github`는 서버 토큰을 사용하지 않는 GitHub 메타데이터 요청으로 현재 공개 여부를 확인한다.
- private가 명시적으로 false이고 요청 저장소 이름과 일치할 때만 진행한다.
- 소스 수집 전후 모두 확인하므로 기존 공개 소스/AST 캐시가 있어도 비공개 전환 후에는 반환하지 않는다.
- 확인 실패 시 서버 PAT를 이용한 대체 승인이나 캐시 fallback을 수행하지 않는다.
- 공개 저장소 분석과 샘플 분석은 유지한다. 수집/AST 알고리즘 자체는 변경하지 않았다.

## 검증 결과

GitHub 응답과 DB는 권한 회귀 테스트에서 mock으로 재현했다. 실제 GitHub 권한 변경 및 운영 DB에 연결하는 검증은 수행하지 않았다.

| 최종 검증 | 결과 |
| --- | --- |
| npm.cmd run typecheck | 통과 |
| npm.cmd run lint | 통과, 경고·오류 없음 |
| npm.cmd test | 30개 테스트 파일 통과, 316개 테스트 통과, 5개 건너뜀 |
| 신규 권한 회귀 테스트 | 위 316개에 포함, 4개 파일 78개 통과 |
| npm.cmd run build | 통과, 컴파일·타입 검사·페이지 생성 완료 |
| git diff --check | 통과 |

건너뛴 5개는 기존 외부 연동 테스트 설정에 따른 결과이며, 실제 GitHub 검증이 통과했다는 의미가 아니다. 빌드가 자동 변경한 next-env.d.ts 및 tsconfig.tsbuildinfo는 작업 시작 상태로 복구했다.

- 신규 회귀 테스트 범위: 설치 삭제/중지, 조직·저장소 접근 회수, Contents 권한 회수, 사용자 토큰 Contents 거부, 다른 사용자 실제 연결 ID 재사용, 비활성 연결, 다른 사용자 설치 행, 인증 만료, rate limit/장애, 불완전/중복/변경된 페이지, 코드 수집/AI 생성 도중 회수, 따뜻한 분석/AI 캐시의 차단, 공개→비공개 전환, 정상 캐시 및 새 분석/AI 생성 유지.
- PowerShell 실행 정책 때문에 npm.cmd를 사용한다. 테스트·빌드는 하위 프로세스 실행을 허용한 환경에서 실행한다.
- 신규 테스트 초기 실행에서 실제 AI 모듈의 server-only 의존성을 테스트 러너가 해석하지 못했다. AI 모듈 전체를 테스트 대역으로 대체한 뒤 재검증했다. 프로덕션 AI 코드는 수정하지 않았다.

## 실제 GitHub 환경의 추가 검증 항목

1. 사용자 A로 개인 비공개 저장소 분석·AI 설명을 생성한 뒤 사용자 B가 A의 실제 연결 ID로 두 API를 요청한다. B는 404여야 하며 분석/AI 내용이 없어야 한다.
2. 조직 App 설치는 유지한 상태로 A를 조직/팀/저장소 협업자에서 제거한다. 기존 ID와 따뜻한 캐시로 요청해도 차단되어야 한다. 단순 조직 구성원이며 특정 저장소 읽기 권한이 없는 사용자도 확인한다.
3. App의 선택 저장소에서 대상 저장소를 제거한다. 이어 설치 일시 중지, 설치 삭제, Contents 권한 제거/승인 대기 시나리오를 각각 확인한다.
4. 조직의 SAML SSO, IP 허용 목록, 외부 협업자 정책, 사용자 액세스 토큰 정책 아래에서 사용자 토큰의 Contents 요청이 거부될 때 설치 토큰이 대신 승인하지 않는지 확인한다.
5. 사용자 GitHub App 승인 취소, 사용자 토큰 만료·갱신·refresh 실패 후 401/503 차단과 재로그인 복구를 확인한다. OAuth 로그인과 App 설치를 별개로 유지하는지 확인한다.
6. 분석 및 AI 캐시를 만든 뒤 권한 회수 전후 동일 요청을 반복한다. AI 생성 또는 소스 수집 도중 권한을 제거하는 시나리오도 확인한다.
7. 서버 토큰이 읽을 수 있는 비공개 저장소를 공개 URL API로 요청해도 차단되는지 확인한다. 공개 저장소를 비공개로 바꾼 직후, 기존 소스/AST 캐시가 있는 상태에서도 확인한다.
8. 저장소 이름 변경/조직 간 이동 후 409 및 목록 동기화 복구, 같은 이름에 다른 GitHub 저장소 ID가 생긴 경우 잘못 승인되지 않는지 확인한다.
9. GitHub 네트워크 장애/403/429/5xx/페이지 중간 실패 시 이전 결과를 대신 반환하지 않는지 확인한다. 복구 후 정상 동기화로 연결이 다시 활성화되는지도 확인한다.
10. Contents 읽기 검사는 빈 저장소/사용 불가능한 기본 브랜치에서 실패할 수 있다. 현재 구현은 안전하게 차단한다. 정상 비어 있지 않은 개인·조직 저장소의 public/private, read/write/admin 권한을 각각 검증한다.

## 운영상 한계 및 주의

- 실제 GitHub 정책·권한 전파 지연은 mock 테스트로 입증할 수 없다. 검사는 요청 시점의 GitHub 응답을 기준으로 하며, 이미 전달된 데이터나 GitHub 측 전파 지연을 되돌릴 수 없다.
- GitHub 권한 확인 요청이 추가된다. 연결 API는 검사 1회당 최소 3요청(설치, 저장소, Contents), 분석 및 새 AI 생성은 처리 후 재검사까지 수행한다. 캐시된 결과라도 권한 확인을 생략하지 않는다.
- 공개 URL은 익명 GitHub API 제한을 받는다. 제한 도달 시 503으로 차단하며 서버 자격 증명으로 검증을 우회하지 않는다.
- 1,000개를 넘는 설치 또는 단일 설치의 접근 가능 저장소는 현재 안전하게 차단한다. 대규모 조직 지원은 전체 페이지 수집 상한과 API 예산을 별도 설계해야 한다.
- 웹훅 및 과거 학습 데이터 삭제 정책은 추가하지 않았다. 권한 회수는 요청별 검사와 기존 동기화 경로에서 반영한다.
