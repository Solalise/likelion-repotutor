# RepoTutor 로컬 IDOR 실행기

Node.js 24 이상에서 추가 패키지 없이 실행한다. 로컬 개발 환경 전용이며 원격 배포·LAN·공인 IP는 지원하지 않는다. 기존 RepoTutor 서버에 프록시 API를 추가하지 않는다.

## 시작

프로젝트 루트에서 터미널 세 개를 사용한다.

```powershell
# 1. RepoTutor (같은 포트에 이미 실행 중이면 재사용)
npm.cmd run dev -- --hostname 127.0.0.1 --port 3100

# 2. 가상 데이터만 사용하는 예제 서버
node tools/security-lab-runner/demo-server.mjs

# 3. 실행기 (통신 4317 / 로컬 관리 4318)
node tools/security-lab-runner/server.mjs
```

1. 실행기 터미널에 출력된 `http://127.0.0.1:4318/#...` 관리 URL을 브라우저에서 연다. fragment는 관리 권한을 가진 임시 비밀값이므로 공유하지 않는다. 화면이 열리면 주소에서 제거된다. 새로고침하면 터미널의 원래 URL로 다시 열어야 한다.
2. 기본 예제 설정으로 등록한다.

| 설정 | 값 |
|---|---|
| 테스트 서버 포트 | 4320 |
| RepoTutor Origin | `http://127.0.0.1:3100` (브라우저 주소와 정확히 일치) |
| A 토큰 / 사용자 ID | `lab-token-a` / `A` |
| B 토큰 / 사용자 ID | `lab-token-b` / `B` |
| 신원 확인 경로 / 사용자 필드 | `/me` / `/user/id` |
| 리소스 ID / 소유자 필드 | `/order/id` / `/order/ownerId` |
| 보호 데이터 필드 | `/order/item` |

3. 테스트 서버·데이터 확인 체크 후 등록한다. 토큰 입력란은 성공 시 비워지고 서버 메모리에만 남는다.
4. `http://127.0.0.1:3100/security-lab/project`를 연다. GitHub 로그인·연결은 필수가 아니다.
5. 실행기 포트 4317과 관리 화면의 일회용 페어링 코드를 입력한다. 코드는 2분간 한 번만 유효하다.
6. API `/vulnerable/orders/{resourceId}`, A/B 리소스 `101`/`102`, 정책 `소유자만 접근 가능`으로 계획을 등록한다. 이 단계까지 대상 요청은 없다.
7. 로컬 관리 화면의 **현재 상태·계획 확인**을 눌러 대상, 신원 확인 2회, 리소스 GET 3회, 정책을 검토한다. 확인 체크 후 현재 계획을 승인한다.
8. RepoTutor에서 **로컬 승인 상태 확인** → 실제 전송 확인 체크 → **승인된 계획 실제 실행**을 누른다. IDOR 재현과 5개 실제 응답의 정제 근거를 확인한다.
9. 경로를 `/fixed/orders/{resourceId}`로 변경하고 새 계획 등록·로컬 승인·실행을 반복하면 접근 차단을 관찰할 수 있다. 이는 예제의 수정 구현 비교다. 자신의 서비스는 같은 경로·같은 테스트 조건을 유지하고 서버를 수정·재시작한 뒤 재검증한다.
10. 종료 시 로컬 관리 화면에서 **설정·토큰·세션 폐기**를 누르고 각 실행 프로세스를 Ctrl+C로 종료한다.

포트 충돌 시 다른 사용자의 프로세스를 종료하지 않는다. 현재 CLI는 기본 포트 4317/4318/4320을 사용한다. 자체 서비스 대상 포트는 관리 화면에서 변경 가능하다.

## 지원 범위와 근거

### VulnLab 내 웹서비스 화면에서 연결

- `/services`에서 서비스를 등록·선택한 뒤, 기존 실행기를 실행하고 터미널에 표시된 로컬 관리 URL을 연다.
- 관리 화면의 대상 포트를 선택한 서비스 포트로, Origin을 VulnLab 화면에 표시된 정확한 Origin으로 설정한다. 기존 테스트 전용 확인·A/B 테스트 계정·응답 필드 설정 절차를 그대로 완료한다. 테스트 Bearer 토큰은 이 로컬 관리 화면에서만 입력한다.
- `/services`의 Runner 통신 포트와 일회용 코드로 페어링한다. 이 화면은 기존 `/v1/pair`, `/v1/state`만 사용하며 계획 등록·승인·실행 API를 호출하지 않는다.
- 선택 서비스 주소와 Runner가 반환한 승인 대상 주소를 정확히 대조한다. 서비스 선택만으로 Runner의 대상이나 승인은 바뀌지 않는다. 불일치하면 관리 화면에서 재설정한 뒤 웹페이지 연결을 해제하고 새 코드로 페어링한다.
- UI의 상태는 마지막 확인 시점의 응답이다. Runner 종료·설정 폐기 여부는 **실행기 상태 확인**으로 갱신한다. 새로고침·화면 이탈·세션 만료 후에는 다시 페어링한다. 등록 목록과 선택만 브라우저에 저장하며, 페어링 세션은 기존 React 메모리 관리 방식을 사용한다.
- 포트 일치와 페어링은 공격 실행 승인이 아니다. 기존 계획별 로컬 승인 절차는 그대로 유지하며, 현재 VulnLab 서비스 화면에는 공격 실행이나 결과 조회를 연결하지 않는다.

- Bearer 인증, JSON 단일 리소스 응답, GET 상대 경로만 지원한다. API 템플릿은 `{resourceId}`를 정확히 한 번 포함해야 한다. JSON Pointer는 `/order/id`처럼 단순 속성·숫자 키만 지원하며 escaped key·필터·코드 실행은 지원하지 않는다.
- 신원 확인 응답에서 관찰한 사용자 ID가 설정한 A/B ID와 일치하고 서로 달라야 한다. 실패하면 리소스 요청을 보내지 않고 판정 불가로 끝낸다.
- A→A, B→B의 정상 응답에서 ID·소유자·보호 필드를 확인한다. 보호 필드는 비어 있지 않은 구별 가능한 테스트 값으로 설정한다. A/B 값이 같거나 필드가 불명확하면 판정 불가다.
- 소유자 전용 정책을 사용자가 선언하고 소유권을 응답과 대조한다. 공유·조직 정책을 자동 해석하지 않는다.
- **IDOR 재현 확인:** A→B 응답에서 B의 ID·소유자·동일한 보호 필드 지문 확인. HTTP 403이어도 데이터가 노출되면 재현으로 처리한다.
- **접근 차단 관찰:** 정상 기준 성공, A→B 403/404, 설정한 리소스·소유자·보호 필드 없음.
- **취약점 의심:** 성공 응답이나 일부 데이터가 있으나 동일한 보호 리소스 노출을 확정할 수 없음.
- **판정 불가:** 인증·신원·소유권·접근 정책 불명확, 정상 요청 실패, 리다이렉트, 네트워크·형식·크기 오류 등.
- 출력은 요청 경로·계정 역할·상태·제한된 ID·보호 필드 SHA-256 지문만 포함한다. 원문 응답·Authorization·Set-Cookie는 웹페이지로 보내지 않는다. 사용자 제공 필드 매핑 밖의 모든 정보 유출을 판별하는 도구는 아니다. 전체 사이트의 안전을 선언하지 않는다.

## 경계와 제한

- 두 실행기 서버와 예제 서버는 `127.0.0.1`에만 바인딩한다.
- 관리 API는 별도 포트·정확한 관리 Origin·임시 관리 비밀값을 요구한다. RepoTutor 통신 세션으로 대상·토큰·승인을 변경할 수 없다.
- 로컬 관리에서 승인한 정확한 HTTP Origin만 CORS 허용한다. `null`·와일드카드·타 Origin을 허용하지 않는다. CORS와 별도로 모든 실제 요청에서 Origin·Host·세션을 검사한다.
- 테스트 대상은 숫자 IP `127.0.0.1`과 로컬 등록 포트로만 생성한다. 경로에 URL·percent encoding·역슬래시·dot-segment를 허용하지 않는다. DNS·시스템 HTTP 프록시·리다이렉트·쿠키·재시도를 사용하지 않는다.
- 실행 계획은 불변으로 생성하고 ID·세션·설정에 묶는다. 변경·재등록 시 기존 승인은 무효이며 승인된 계획은 한 번만 실행한다. 실행 중 설정 변경은 거부한다.
- 페어링·계획 승인 유효시간 2분, 세션 10분. 만료 시 비밀값 참조를 폐기한다. 문자열 메모리의 물리적 덮어쓰기까지 보장하지는 않는다.
- 신원 확인 2회 + 리소스 3회로 최대 5회, 동시 실행 1개, 실행 간격 최소 5초. 요청마다 절대 제한 4초, 응답 최대 64KiB, 응답 헤더 최대 8KiB. 세션의 남은 시간이 실행 상한보다 짧으면 실행을 거부한다.
- 브라우저 세션과 계획은 메모리에만 존재하며 새로고침하면 다시 연결해야 한다. 테스트 토큰은 RepoTutor 서버·DB·localStorage·로그·GitHub 인증과 연결하지 않는다.
- 원격 RepoTutor 페이지·터널·Vercel 대상은 미지원이다. 브라우저의 로컬 네트워크 권한·CORS 정책으로 연결이 거부될 수 있다. 보안 기능을 끄지 말고 지원되는 로컬 개발 환경에서 실행한다.
- GET도 대상 구현에 따라 부작용이 있을 수 있다. 사용자 소유의 테스트 서버와 가상 계정·데이터만 승인한다. 로컬 주소만으로 실제 운영 DB 미연결을 기술적으로 보장할 수는 없다.

## 검증

```powershell
node --test --test-isolation=none tools/security-lab-runner/runner-check.mjs
npm.cmd run typecheck -- --incremental false
npm.cmd test -- --maxWorkers=1 --testTimeout=15000
```

실행기 검증은 실제 루프백 HTTP 서버를 생성하고 페어링·로컬 승인·실제 요청·결과를 검사한다. 대상 HTTP는 mock이 아니다. Node 테스트 파일은 Vitest와 혼합하지 않도록 별도 이름과 실행 명령을 사용한다.
