# VulnLab Side Panel (개발자 모드)

1. VulnLab 웹서비스를 실행하고 GitHub 저장소를 분석합니다.
2. Chrome 116 이상에서 `chrome://extensions` → 개발자 모드 → **압축해제된 확장 프로그램 로드** → 이 `extensions/vulnlab` 폴더를 선택합니다. 별도 빌드가 필요 없습니다.
3. 내 웹서비스 보안 검증 화면으로 이동합니다. 사이트 등록은 선택이며 소유권 확인 없이 교육 가이드·수동 기록을 이용할 수 있습니다. Vercel 계정 연결은 필요하지 않습니다.
4. 확장 관리 화면에 표시된 ID를 VulnLab 웹 화면에 입력하고 **검증 가이드 준비 및 확장 연결**을 누릅니다.
5. Chrome 도구 모음의 VulnLab 아이콘을 눌러 우측 사이드 패널을 엽니다. 사이트를 등록했다면 **등록 사이트 열기 (일반 탐색)**로 열 수 있습니다. 네 가지 유형을 전환하며 단계별로 검토합니다. VulnLab 탭은 열어 둡니다.
6. 마지막 단계에서 기대·관찰 결과, 근거, 필요시 해당 없음 사유를 입력하고 수동 기록을 저장합니다. **DB 저장 완료** 표시 후 기존 VulnLab `/results` 목록에서 기록을 확인합니다. 기록 저장은 실제 보안 검증 완료가 아닙니다.

## VulnLab 주소 설정

기본 연결 허용 주소는 `http://localhost:3000`, `http://127.0.0.1:3000`입니다.
다른 주소에서 VulnLab을 실행하면 **VulnLab 앱 주소만** 다음 두 곳에 명시적으로 추가하고 확장을 다시 로드하세요.

- `config.js`의 `appOrigins`: 정확한 origin (예: `https://vulnlab.example.org`). 포트가 다르면 포트도 명시합니다.
- `manifest.json`의 `externally_connectable.matches`: 같은 호스트의 패턴 (예: `https://vulnlab.example.org/*`). Chrome 매치 패턴의 포트 제약은 `config.js`의 정확한 origin 검증으로 보완합니다.

테스트 사이트 주소는 허용 목록에 넣지 않습니다. `*://*/*`, `<all_urls>` 등 광범위한 패턴을 추가하지 마세요.

## 범위·데이터 처리

- 권한은 `sidePanel` 하나입니다. content script, host permission, cookies, tabs 읽기 권한, 외부 HTTP 요청 코드가 없습니다. `tabs.create`는 사용자 버튼으로 검증된 URL을 여는 용도로만 사용합니다.
- 로그인된 웹 탭이 기존 동일 출처 API를 호출합니다. 확장에는 로그인 세션·쿠키·토큰을 전달하지 않습니다. 저장·사이트 열기 직전 기존 API로 저장소 접근 권한과 사이트 등록 버전을 다시 확인합니다. 소유권 확인은 기본 가이드 이용 조건이 아닙니다. 확장 연결·일반 탐색·수동 기록은 외부 실행 승인이 아닙니다. 기존 능동적 테스트 실행 승인과 외부 요청 제한은 유지합니다.
- 세션은 저장소 연결·분석 SHA·테스트 환경 버전에 묶입니다. 코드 근거는 실제 후보/관찰 지점의 제한된 발췌이며 자격증명 패턴이 감지된 발췌는 제외합니다. 사용자 기록도 기존 자격증명 방지 검사를 거칩니다. 자동 탐지는 모든 비밀 형식을 보장하지 않으므로 비밀정보를 기록하지 마세요.
- 확장 디스크 저장소를 사용하지 않습니다. 탭·확장 연결 종료 또는 패널 종료 시 저장 전 초안은 소실될 수 있습니다. 패널 진행률은 현재 패널에서 저장한 유형 수이며 이전 DB 기록 전체를 복원한 점수가 아닙니다. DB 기록은 기존 목록/웹 보조 화면에서 조회합니다. 다시 저장하면 이전 기록을 보존하는 새 수동 기록이 추가됩니다.
- 후보 0개, 미지원, 분석 실패를 구분합니다. 실제 취약점이나 서비스 전체 안전성을 확정하지 않습니다. 합성 데이터·승인된 비운영 격리 환경에서 사용자가 직접 검토합니다. 소유권 확인은 격리 여부나 배포 커밋 동일성의 자동 증명이 아닙니다.
- 기존 소유권 검증이 허용하지 않는 localhost/사설 주소 대상 검증을 우회하지 않습니다. 확장 연결용 localhost VulnLab 주소와 검증 대상 사이트 주소는 별개입니다.
- 종합 분석, 재검증, 웹스토어 배포 및 패널에서 과거 기록 복원은 이번 범위에 포함하지 않습니다.

## 직접 확인

- 확장 로드 → 아이콘 클릭 → 패널 열기. 미설치·잘못된 ID·허용되지 않은 VulnLab origin은 연결되지 않는지 확인합니다.
- 소유권 미확인·사이트 미등록 상태에서 확장 연결과 네 유형 가이드·수동 기록 저장이 가능한지 확인합니다. 사이트 미등록 시 열기만 비활성화되고, 등록 시 일반 탐색으로만 열리는지 확인합니다. 후보 0개 프로젝트의 네 유형 접근, 실제 파일/줄/코드 일치를 확인합니다.
- 유형 전환 시 작성 중 관찰 초안 유지, 이전/다음 단계, 해당 없음 사유, 저장 성공 후 `/results`의 수동 기록을 확인합니다.
- 연결 탭 종료·로그아웃·저장소 접근 해제·테스트 URL 변경 후 저장/사이트 열기 실패가 표시되는지 확인합니다. 패널이 브라우저 설정에 따라 왼쪽에 있다면 Chrome 사이드 패널 설정에서 오른쪽으로 변경하세요.

API 근거: [Chrome Side Panel](https://developer.chrome.com/docs/extensions/reference/api/sidePanel), [외부 연결 허용](https://developer.chrome.com/docs/extensions/reference/manifest/externally-connectable), [메시지 전달](https://developer.chrome.com/docs/extensions/develop/concepts/messaging).

## 프로젝트별 AI 가이드

- 기존 서버 환경변수 `GROQ_API_KEY`를 그대로 사용합니다. 추가 키는 필요 없습니다. 모델은 기존 `GROQ_MODEL`, 시간 제한은 `GROQ_TIMEOUT_MS`(기본 25초, 최대 60초)를 사용합니다. 미설정 시 서버 `.env`에 `GROQ_API_KEY=...`를 설정한 뒤 서버를 다시 시작하세요. `NEXT_PUBLIC_` 접두사는 사용하지 않습니다.
- 가이드 준비 버튼을 누르면 인증된 웹 탭이 분석 커밋만 서버에 전송합니다. 서버는 저장소 권한과 완료된 분석 기록을 확인하고 서버 분석 캐시에서 근거를 가져옵니다. 분석 캐시가 만료되면 웹에서 기본 가이드로 대체하며 재분석 안내를 표시합니다.
- 기존 AST 함수·import·호출·참조·페이지 진입점·Server Actions를 기능 단위로 묶습니다. 함수 본문의 입력·DB·출력·인증·역할 구문을 실제 줄 번호로 추출합니다. 정적 참조가 확인돼도 런타임 입력 전파나 저장 후 출력까지 확정하지 않습니다. XSS는 입력과 출력이 연결된 기능을 우선하고, 해당 기능이 있으면 정적 소개 컴포넌트는 제외합니다.
- AI에는 유형별 최대 16개, 발췌별 최대 350자의 마스킹된 코드와 기능별 역할·근거 참조만 전달합니다. 저장소 전체 코드, 프로젝트 이름, 원본 파일 경로, 사이트 URL은 전달하지 않습니다. 문자열·숫자 리터럴, 주석, 비공개 식별자를 마스킹하고 자격증명·이메일이 감지된 근거는 제외합니다. 실제 이름과 위치는 서버가 검증한 참조로 연결합니다.
- AI는 카드 ID 선택 대신 기능별 행동·준비물·기대값·관찰법·결과별 해석을 문장으로 작성합니다. 서버는 기능/근거 ID, 필수 입력·출력/DB/역할 인용, 길이, 이름·경로·공격 지시 등을 검사하고 실제 코드와 기능명을 붙입니다. 관리자 역할이 관찰되지 않으면 관리자 전용으로 가정하지 않습니다. 업무 정책과 런타임 전달은 미확인으로 남깁니다. 자유 문장의 모든 의미를 자동 증명하는 방식은 아니므로 AI 설명은 코드 근거와 함께 검토해야 합니다.
- 긴 응답의 구조 오류를 줄이기 위해 캐시 미스 때 관련 코드가 있는 유형별로 작은 Groq 요청을 순서대로 생성합니다. 관련 코드가 없는 유형은 AI를 호출하지 않습니다. 사용자·저장소 연결·분석 SHA·근거 지문·모델·프롬프트 버전 기준으로 24시간 프로세스 메모리 캐시를 재사용하고 동시 요청을 합칩니다. 실패는 5분 캐시합니다. 서버 재시작·인스턴스 변경 시 캐시는 공유되지 않습니다. 신규 DB 구조나 인프라는 추가하지 않았습니다.
- AI 응답은 내부의 두 고정 슬롯으로 검증하고 표시 단계는 별도로 분해합니다. 확인된 코드 역할에 따라 3~5단계 등이 될 수 있으며 해당 없음·미지원·미확인은 범위 확인 1단계입니다. 매 단계에서 결과와 확인 방법을 선택하고 마지막 단계에서 자동 집계된 미리보기를 확인해 저장합니다. 미선택 단계와 근거 미확인은 판정 불가로 남기며 실제 검증 완료로 집계하지 않습니다. 기록은 기존 DB의 수동 관찰/근거 필드에 모아 저장합니다.
- 기본 모델의 [엄격한 JSON Schema 응답](https://console.groq.com/docs/structured-outputs)을 사용하고 문장·근거는 별도로 검증합니다. 이번 합성 코드 실호출에서는 형식 검증 실패와 Groq `json_validate_failed` 400 오류가 관찰됐습니다. 해당 응답은 사용하지 않으며 기능 기반 기본 가이드로 대체됩니다. 실제 AI 생성 성공을 확인한 것으로 보고하지 않습니다.
- 실제 생성된 **기본 가이드** 예시는 `docs/security-review-guide-examples.json`에 있습니다. 사용자 저장소가 아니라 문의 기능을 재현한 로컬 합성 fixture의 결과입니다. 기본 테스트는 모의 API만 사용하며, 수동 실호출 검증은 기존 `RUN_ACTUAL_REPO_AI=1`로 예시 테스트 파일만 실행할 때 작동합니다.
- 변경 후 `chrome://extensions`에서 확장과 VulnLab 웹 페이지를 새로고침해 다시 연결하세요. 실제 저장소의 기능 선택·줄 번호·단계별 집계와 시각적 배치는 직접 확인해야 합니다. 추가 환경변수는 필요하지 않습니다.

## 고정 응답 슬롯과 표시 단계

- AI 전송 형식의 `review`·`observe` 두 슬롯은 응답 구조를 안정화하는 내부 규약입니다. 기존 근거·문장 안전 검증을 통과한 뒤 서버에서 표시 단계를 구성합니다.
- 표시 단계 수는 슬롯 수와 다릅니다. 예를 들어 근거가 있는 XSS는 기능 확인 → 입력 처리 코드 → 출력 코드 → 환경·합성 데이터 준비 → 관찰의 5단계가 될 수 있습니다. 객체 접근·역할 검토는 관련 코드 구문이 있으면 4단계, 해당 없음·미지원·근거 부족은 범위 확인 1단계입니다. 없는 코드 역할을 채우기 위해 단계를 만들지 않습니다.
- 세부 단계는 원래 검증된 기능과 인용된 코드 집합 안에서만 나눕니다. 준비가 완료됐다는 사실이나 관찰 결과를 자동 생성하지 않습니다. 기본 가이드 내용도 원본을 수정하지 않고 같은 표시 계층에서 필요한 경우 나눕니다.
- 캐시에는 검증된 내부 결과를 보관하고 표시 단계는 서버에서 계산합니다. 단계 이동이나 표시 단계 분해 자체는 AI를 호출하지 않습니다. 실제 Groq 실생성은 아직 실패 사례가 남아 있으며, HTTP 200만으로 AI 가이드 성공으로 처리하지 않습니다.
